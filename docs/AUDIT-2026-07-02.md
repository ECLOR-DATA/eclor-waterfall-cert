### F1 — fx-resolved / DataView-persisted fill colours are injected into SVG attributes with neither safeHex nor attribute escaping — violates the documented 'safeHex on every ColorPicker value' invariant and can silently kill the whole frame [M]

**Preuve :** extractFill (src/visual.ts:5870-5879) returns the raw string from DataView objects with no validation. Raw values flow to SVG attribute injection at: rail bars fill="${rectColor}" (src/visual.ts:4212, from rail.colorPos/colorNeg built at src/visual.ts:2488-2505), rail name/label text via fontAttrs fill (src/visual.ts:4190, 4238), pillar fill="${pillarColor}" (src/visual.ts:4467, from cat.pillarColor = fxAcrossRows -> extractFill, src/visual.ts:2126-2146), bridge fill="${color}" (src/visual.ts:4628 via perRowBridgeColor at 4550-4554), legend segment stacks (src/visual.ts:4427, 4582 from seg.color) and legend swatches fill="${lv.color}" (src/visual.ts:5170, 5197, from legendValues color: persisted || themedDefault at src/visual.ts:2828 where persisted = extractFill(rowObj.itemColor), 2797), svgLabelBg fill="${bgColor}" (src/visual.ts:5783), fontAttrs fill="${color}" (src/visual.ts:5855 — note the SAME helper escapes font-family via escapeXmlAttr at 5856, so attribute safety was considered there). The codebase is internally inconsistent: the variation-arc path DOES wrap the identical fx-resolved values in safeHex/safeHexOrEmpty (src/visual.ts:4846-4856), the rails/pillars/bridges/legend paths do not. CLAUDE.md states 'safeHex() validates every ColorPicker value before injection. No exceptions.' A conditional-formatting 'Field value' rule makes the fill a data-derived arbitrary string (a DAX measure result), so a value containing a double quote breaks out of the attribute; the repo's own comment at src/visual.ts:5051-5056 documents the consequence of a malformed attribute: DOMParser <parsererror> -> the frame silently fails and the visual freezes on the previous frame.

**Changement proposé :** Zero-behaviour-change fix: route every raw-fill injection through the existing escapeXmlAttr helper (src/visual.ts:5863). Concretely: (a) in fontAttrs change fill="${color}" to fill="${escapeXmlAttr(color)}" (5855); (b) same in svgLabelBg for bgColor (5783); (c) wrap the seven rect-fill template sites (4212, 4427, 4467, 4582, 4628, 5170, 5197) — or, cheaper, apply escapeXmlAttr once at the source: return escapeXmlAttr(...) from extractFill (5870), which covers every consumer including patchFxSlice-independent render paths. escapeXmlAttr (not safeHex) preserves legitimate named-colour / rgb() Field-value fx fills that safeHex would reject, while making attribute breakout impossible. Add one jest case: a variance colorPos override containing '"/><rect' renders a parseable frame.

**Risque :** Near zero with escapeXmlAttr (valid colours are unchanged; hostile strings become inert invalid-colour no-ops instead of a dead frame). If safeHex were used instead (arc-path parity), named-colour Field-value fx rules on bridges/pillars would silently fall back to defaults — a behaviour change for existing reports; do not pick that variant without deciding it explicitly.

**Corrections du vérificateur :** Two minor precision notes, neither affecting the verdict: (1) the pillar-colour resolution feeding the fill at 4467 sits at ~4330-4337 (perCatPillarColor || defaultPillarColor), slightly above the finding's cited 4348-4350 region — same chain, same conclusion. (2) The 'cheaper' variant of escaping at the source (extractFill returning escapeXmlAttr(...)) also feeds Format-pane patchFxSlice values (src/visual.ts:1461-1517); identity for valid colours, but the per-site escaping variant (a)-(c) is the cleaner implementation since it keeps parse-layer data un-mutated.

### FM-3 — connectorWidth and barWidth are the only two NumUpDowns without min/max options — negative typed values reach the SVG as invalid negative widths [S]

**Preuve :** settings.ts:652-656 (connectorWidth) and settings.ts:682-685 (barWidth) construct NumUpDown with no options block; every other NumUpDown in the file declares minValue/maxValue (fontSize 6-60, yMinOffset 0-95, railHeight 40-140, lineWidth 1-6, arrowSize 0-14, transparencies 0-100, etc.), so the pane clamps those but not these two. ## perf (6)

### PERF-1 — Cross-highlight remap is O(rows x uniqueCats) via orderedCatLabels.indexOf inside a forEach over highlighted rows [S]

**Preuve :** src/visual.ts:2435-2443 — `highlightedCatIdxs.forEach((rowIdx) => { const label = String(cats[rowIdx] ?? ""); const idx = orderedCatLabels.indexOf(label); ... })`. highlightedCatIdxs is a Set of LEAF-ROW indices built at src/visual.ts:2301-2310 from the highlights array — during an external cross-highlight it typically contains most/all rows (up to the 10k cap). orderedCatLabels holds the unique category labels; with no legend/adim split, uniqueCats == rows. Confirmed indexOf is a linear scan over that array, executed once per highlighted row, on every update while another visual cross-highlights this one.

**Changement proposé :** Build a `labelToCatIdx = new Map<string, number>()` in the same loop that already constructs catRowsByLabel/orderedCatLabels (src/visual.ts:2397-2406, and re-populate after the showEmpty filter at 2409-2423), then replace `orderedCatLabels.indexOf(label)` with `labelToCatIdx.get(label)`. Same String(cats[rowIdx] ?? "") key on both sides, so semantics are identical.

**Risque :** Very low — pure lookup-structure swap with identical keys. Only care point: the map must be rebuilt (or filtered) after the showItemsWithNoData drop so indices match the post-filter orderedCatLabels. Worst case today: 10k highlighted rows x 10k unique labels = 1e8 string compares (~0.5-2s of main-thread jank) on every cross-highlight update; typical 10k x 50 = 500k compares. The fix makes it O(rows).

**Corrections du vérificateur :** Three corrections to the finding's framing, none fatal: (a) Worst-case magnitude is overstated — with unique labels each indexOf terminates at the label's own position, so the total is ~n²/2 ≈ 5e7 string compares at the 10k cap, not 1e8; realistic jank is more like ~100-500ms, not 0.5-2s. (b) The pathological case (10k unique categories) means the visual is also rendering ~10k SVG bars, which dominates the frame cost anyway — the user-visible win is limited to extreme datasets; at typical waterfall scale (≤ a few hundred unique cats) the current code is already negligible, as the finding's own 'typical' math admits. (c) Simpler fix variant: build the labelToCatIdx Map once immediately before the remap block (after the showEmpty filter, ~line 2434) rather than maintaining it through both earlier loops — this sidesteps the rebuild-after-filter subtlety entirely and is ~4 lines. Bonus same-class issue in the same function the finding missed: the showEmpty filter itself is O(n²) via `filteredOrderedCatLabels.includes(label)` at visual.ts:2416 inside a loop over orderedCatLabels; converting filteredOrderedCatLabels to a Set in the same patch fixes both quadratics. Effort: XS (single-function change, existing highlight tests in test/ cover the remap semantics).


### PERF-2 — showItemsWithNoData drop path is O(uniqueCats^2) via Array.includes inside a loop over all labels [S]

**Preuve :** src/visual.ts:2409-2423 — when showEmpty is false and at least one category is dropped: `for (const label of orderedCatLabels) { if (!filteredOrderedCatLabels.includes(label)) { catRowsByLabel.delete(label); } }`. `includes` is a linear scan of the filtered list, inside a loop over the full list. With the matrix mapping, orderedCatLabels can reach 10k entries (every leaf a distinct category, e.g. date grain, sparse measure producing null rows). Verified the branch only triggers when lengths differ, i.e. exactly the sparse-data case.

**Changement proposé :** Replace with `const keep = new Set(filteredOrderedCatLabels); for (const label of orderedCatLabels) { if (!keep.has(label)) catRowsByLabel.delete(label); }` — one extra Set allocation, identical semantics (labels are already unique strings).

**Risque :** None discernible — Set.has on the same string values. Worst case today: 10k x ~10k = up to 1e8 string compares per update on sparse datasets at the cap; the fix is O(U).

**Corrections du vérificateur :** Minor precision: worst case is O(U×F) (kept-list scans), ~1e8 compares only when most of 10k categories are kept and a few dropped; matches hit V8's reference-equality fast path since filtered holds the same string objects, so real cost is dominated by the misses — still a genuine quadratic worth fixing, effort trivial. Note the same pattern recurs a few lines below (orderedCatLabels.indexOf inside the highlight-remap forEach, visual.ts:2439) — a highlight-path O(H×U) scan the same Set/Map approach could cover, though it only runs during cross-highlight.

### PERF-5 — resolveCategoryFx does 16 full row-scans per category (8 props x 2 tally passes) even when no per-row fx objects exist at all — >1M wasted probes per update in the common no-fx case [S]

**Preuve :** src/visual.ts:2095-2157 — per category, fxAcrossRows is called 8 times (2146-2155); each call sums `rowSigned` over all the category's rows (2101-2102, a Number() conversion per row), then runs tally(true) and — since no fill is found — tally(false) again (2136-2137). Each tally visits every row and probes every category-column AND value-column objects array (2124-2131). When NO fx rule/constant is persisted (the common case), all those arrays are empty ([] from `c.objects || []` at 2347-2359) and every probe returns undefined, but the loops still run: at 10k leaf rows with 3 cat + 5 value columns that is 8 props x 2 passes x 10k rows x 8 probes ≈ 1.28M probes + ~240k redundant Number() conversions per update (and again per table-row focus via 2025). The 4-layer cascade itself is documented-deliberate — this finding does not touch its order or layers, only short-circuits when every per-row layer is literally empty.

**Changement proposé :** (1) Precompute once in fxCtx (src/visual.ts:2549-2556): `hasRowObjects = allCatColObjects.some(a => a.length > 0) || allValueColObjects.some(a => a.length > 0)`; in resolveCategoryFx return the all-undefined CategoryFxColors immediately when false — provably identical output since empty arrays can never yield a fill. (2) While at it, hoist the signed bases: precompute `signedActual[r]` and (comparison only) `signedBridge[r]` arrays once per parse so rowSigned becomes an array read instead of repeated Number(??0) over the same PrimitiveValue arrays.

**Risque :** Near zero for (1) — the gate is exactly "no per-row objects anywhere", which already yields undefined through the slow path; the documented sign-aware vote is untouched when fx IS present. (2) is a pure caching of deterministic conversions; only risk is drift if a future change mutates actualVals mid-parse (nothing does today).

**Corrections du vérificateur :** Minor: (1) each fxAcrossRows call actually makes up to 3 row passes per prop (agg sum + 2 tallies), not just the 2 tally passes — this is what makes the ~240k Number() figure correct; (2) the table-row focus path at src/visual.ts:2025 re-scans only the focused category's rows, so its cost is proportionally smaller than a full-update rescan; (3) the gate is safer written as some(a => a.length > 0) exactly as proposed, though a.some(o => o != null) would additionally guard hypothetical all-null padded arrays — either is behavior-preserving.
